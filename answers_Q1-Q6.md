### Analytical & Forensic Engineering Responses

- **Question 1 (Memory Coalescing & Strided Column Packing):** The array is row-major, so element (i, j) sits at byte offset `8*(i*258+j)`. The cells of column 1 (rows 1..256) are therefore 2064 bytes apart: one useful float64 per row, with 257 unused elements between neighbours. A single DMA descriptor describes one contiguous range, so it cannot select such a column. At warp level, 32 threads reading a column touch 32 different 128-byte segments (one useful 8 B word each: 32 transactions instead of 2), which is why the pack kernel reads the column once on the device and writes it to a contiguous 1D buffer, so the PCIe copy is a dense 2048-byte transfer. If one copied the bounding range from u[1,1] to u[256,1] instead, it would span `(256-1)*258+1` = 65791 elements = 526328 bytes, of which only 2048 are useful, i.e. **524280 extra bytes per column** (about 257x overhead); the same happens for the right column.

- **Question 2 (Shared-Memory Tile Indexing & Bank Conflict Analysis):** Thread (tx=0, ty=0) writes its centre to smem[1,1]; since ty==0 it also writes smem[0,1] (= u[i-1,j]) and since tx==0 it writes smem[1,0] (= u[i,j-1]); in the stencil it reads smem[1,1], smem[0,1], smem[2,1], smem[1,0], smem[1,2]. Thread (tx=15, ty=15) writes smem[16,16], plus smem[17,16] (ty==15) and smem[16,17] (tx==15); it reads smem[16,16], smem[15,16], smem[17,16], smem[16,15], smem[16,17]. Element (sy, sx) of the 18x18 float64 tile occupies 32-bit words `2*(18*sy+sx)` and the next one, so its bank is `(36*sy+2*sx) mod 32 = (4*sy+2*sx) mod 32`. A 64-bit access by a warp is serviced as two half-warp (16-thread) wavefronts. In a half-warp all threads share one ty, so a row access (smem[ty+1, tx+k]) hits 16 consecutive 8-byte words = 128 B = all 32 banks exactly once, and the vertical-neighbour reads smem[ty, tx+1] / smem[ty+2, tx+1] are also row accesses. Result: no bank conflicts; the 2 wavefronts per 64-bit request are the normal cost of 64-bit data on Turing (CC 7.5), not a conflict. Only if both rows of a warp were serviced together would the row stride of 36 words (= 4 mod 32 banks) cause a 2-way overlap, and the hardware does not do that for 64-bit loads.

- **Question 3 (PTX Assembly Audit & Warp Synchronization):** Counts from `tiled_stencil_kernel.inspect_asm()` in my run: **st.shared.f64 = 5, ld.shared.f64 = 5, bar.sync = 1** (ptx_audit_passed = True). A 16x16 block has 8 warps (32 threads = two tile rows each), and warps are scheduled independently. Without `cuda.syncthreads()`, a warp that has finished loading may start reading smem[ty, tx+1], smem[ty+2, tx+1], etc. before other warps have written their rows/apron cells, so it reads uninitialised or stale shared memory (a read-after-write race), giving non-deterministic results that depend on scheduling. The barrier guarantees all 8 warps have completed their stores before any warp loads.

- **Question 4 (Multi-Process Context Sharing on a Single Physical GPU):** Four OS processes each own a separate CUDA context on the same T4. Contexts are time-sliced by the GPU (no true concurrent SM sharing across processes without MPS), so kernels from different ranks are serialised at the context level and the SMs are not split between them; the copy engines (DMA) are likewise shared. Measured: serialized_ms = 1658.09 ms vs overlapped_ms = 2032.80 ms (0.816x; CUDA-event times 1656.73 / 2032.65 ms). In my run overlap did not help but hurt: the overlapped step adds an extra stream synchronization and five kernel launches per step (one interior plus four ring launches on tiny 256-cell strips that fill only a few blocks), and the interior kernel on stream_interior competes with the other three processes' contexts, which the GPU time-slices rather than runs concurrently. The 2048-byte halo messages travel host-to-host through shared memory in microseconds, so there is almost no communication latency left to hide, and the overhead exceeds the gain. With four dedicated GPUs over InfiniBand each rank has its own SMs and DMA engines, and the network latency (microseconds plus staging) is large relative to the interior compute, so the overlap hides it and the gain is much larger.

- **Question 5 (Point-to-Point Message Deadlock & MPI.PROC_NULL Semantics):** `MPI_Send` may return early only if the message is buffered (eager protocol, below an implementation threshold, a few KB for shared-memory transports, tunable via ompi_info parameters). Above the threshold the rendezvous protocol is used and Send blocks until the matching Recv is posted. If every rank calls Send first in the same directional order, then in the 2x2 grid rank (0,0) blocks sending down to (1,0) while (1,0) blocks sending up to (0,0): both are in Send, nobody is in Recv, which is a circular wait. For small messages (our 2048 B) the eager buffer hides this, so the code may appear to work and then hang when the grid grows; non-blocking Isend/Irecv posted before Waitall removes the ordering dependency. `MPI.PROC_NULL` as source/dest makes Send/Recv/Isend/Irecv complete immediately with no data transfer, so on corner rank (0,0) (up = left = PROC_NULL) the same code runs for all ranks without if-branches; the receive buffer is left untouched, so the ghost cells stay at the Dirichlet value 0.

The simulation used dt = **1.979086e-06** = 0.50 * dt_max < dt_max, so the diffusion part is within the explicit stability limit (the cubic damping term only makes the system more dissipative for u>0).
